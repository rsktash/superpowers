### (2026-08-19) Decision Beads gains a triage step; two incident parentheticals displaced here.
RULE CHANGE: forks are parked ONLY as decision beads with dep-links, and are triaged under
  precedence (ruling > code > spec > plan-time text) BEFORE being parked. Re-reading an
  inherited fork list re-runs the triage. Also: a gate's factual premises must not contradict
  the spec text they derive from or a standing ruling, not merely "evidence already gathered".

### (2026-09-04) The exploration map: symbol rows written once at plan time, freshness computed at dispatch.
RULE CHANGE: a new Checklist step (5, Exploration Map) writes docs/beads/<epic-id>.map.md in the
  target repo — one row per cited or created symbol, the Hash cell holding exactly one of two
  values (the 12-hex hash scripts/structural-index prints at the planning commit, or the literal

### (2026-09-05) Decision Beads: a fork is one typed, bylined command, and the planner never answers it.
RULE CHANGE: the fork create is one command — bd create "Decide: <fork>" --parent <root>
  --question "<fork>" --topic <slug> — so bead and question land in one transaction and the
  attached question holds the bead out of bd ready; the Decide bead is then dep-linked in front
  of every task the outcome blocks. The forked planner exports BD_ACTOR=planner before its first
  bd write and holds it for the whole run (R-A/R-37), so bd bylines its questions and findings
  planner and refuses its rulings. Topic slugs are picked, not invented: reuse a slug bd topics
  prints, mint only when none fits (R-D/R-40 restricts minting to owner, coordinator, planner).
  The two remaining paths are stated once each — a fork on an already-created task is
  bd question add <task-id> "<fork>" --topic <slug>, and the answer is the coordinator's or the
  owner's bd ruling add <decide-id> "<text>" --answers <Q-id> --close.

INCIDENT: the section's own command had stopped working. Verified 2026-09-05 on a scratch
  database: bd create "Decide: …" --parent <root> exits 1 with 'a "Decide:" bead needs the
  question attached', and --question without --topic exits 1 with '--question requires --topic'
  — so the two-step the section prescribed (create, then bd question add) could not even reach
  its second command. In the same run, with BD_ACTOR unset a planner's questions carry the
  owner's byline; under BD_ACTOR=planner they carry planner:<user> and bd ruling add is refused
  ("executors cannot file rulings"), while bd create, bd dep add, bd label add and
  bd update --body-file all succeed — every verb the skill tells the planner to run.
